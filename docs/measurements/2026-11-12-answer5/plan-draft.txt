every run
  KVID_INDEX_MEASURE=corpus=mixed+notes=5000+<configuration>+edits=200+queries=200+pause=300
  queries=200 is kept: a multiple of 4, so each of the four query call orders is used 50 times.
  Phase order in the test: open, index, pause, queries, edits, close.
  Fresh instrumentation process, same APK, model files as in Phase B. At the start of a run: launcher in front,
  screen on (the driver sends the wake key if it finds the screen off, and notes it), phone not charging (state
  recorded in each gate line; a run does not start while it charges). The driver does not hold the screen on
  during a run; the phone's own screen timeout applies, as in Phase B.

captured per run
  adb logcat -d -s System.out | grep -E "\[kvid-(index-measure|index-samples|embedding-tune)\]"
  kept whole in one raw file per run: the result line and all its [kvid-index-samples] lines.

checker, after every run and before the next one starts
  python3 -I kvid-embed-onnx/scripts/check_measure_lines.py <the run's raw file>     (script at 31f1e0c)
  It must print OK. A failure is a harness fault, not an exclusion: the queue stops, nothing further is run, and
  the raw file and the checker's output go to the cloud session. The same holds for an instrumentation run that
  does not end "OK (1 test)".
  Codex's second review found that the checker at 31f1e0c does not recompute the by-token-length percentiles.
  Unless a later checker does, the analysis recomputes them from the edit_tokens and edit_total_ms samples and
  compares them with the line; a difference is reported as a harness fault.

unit and order (step 3, Pixel 8)
  The unit is a block of two runs, one per configuration. Order by block: AB, BA, AB, BA.
  At least three valid blocks, over at least two sessions; the fourth if the phone is available.
  A session is one attachment of the phone. At most two valid blocks in one session, so that three blocks
  always span two sessions.
  A block that loses a run is listed as excluded and repeated whole under a new label (b1, b1r1, b1r2), at
  most three attempts per block; its remaining runs are not made.
  Roughly 45 to 60 minutes per run with its cooling wait, so a block needs about two hours of attachment.

cooling rule (fixed here; do not reuse either Phase B rule for the Pixel 8)
  Baseline at the start of each session: phone at its charge limit and not charging, launcher in front, screen on,
  nothing run by the driver for at least 20 minutes, VIRTUAL-SKIN read every 60 s.
  A reading counts when the thermal status is 0, the launcher is in front and the phone is not charging; a
  reading that does not count restarts the count. The baseline ends after 21 counted readings in a row; if that
  does not happen within 2 hours the session is not run. A screen found off gets the wake key and is noted.
  Idle level = median of the last 15 readings. Threshold = idle level + 0.5 C, rounded to 0.1 C.
  A run starts only at thermal status 0 with skin at or below the threshold; gate timer 2 hours.
  The threshold of a later session is computed the same way and recorded. If it differs from the first session's
  by more than 1.0 C the session is not run and that is reported. No other change to the rule; if the phone
  cannot reach it, the runs are not made.

exclusions (decided by these rules only, never by a result)
  another app in front before, during or after the run (driver's check);
  a start outside the rule, or while charging;
  the phone leaving during the run (no line);
  a line whose settings differ from the queue's.
  Excluded runs keep their raw lines and are listed with the reason.
  A checker failure is not on this list: see "checker".

thermal logging
  Battery and skin temperature and thermal status before, every 15 s during, and after each run. Every reading is
  stamped with the phone's clock (epoch ms, `date +%s%3N` in the same adb shell call as the reading) and with host
  UTC. At each gate the phone-to-host offset is also recorded (phone epoch ms between two host readings).
  Alignment: a phase starts at open_epoch_ms + 1000 * its phase_start_s value, on the phone's clock. The reading
  reported for a phase start is the last one at or before that time, with its age in seconds.
  Reported per run: thermal status and skin temperature at the start of the index, queries and edits phases, and
  the number of readings at status 1 or above in each phase.

reported per configuration (fixed now)
  edit_total p50 and p95 against 200 ms, overall and by token length:
    per run, from the result line;
    pooled: the nearest-rank p95 over all counted calls of the configuration's valid runs (600 calls for three
    runs), computed from the edit_total_ms samples, shown beside each run's p95;
    by kind (put, update) from edit_kind, per run and pooled the same way.
  query_embed and query_hybrid p95, per run and pooled the same way, at query_store_notes notes. Described as
    warm calls on a synthetic vocabulary in rotated order, not as representative search latency.
  mem_lifecycle_peak_kb in KiB and decimal MB against 488,281 KiB, stated as a sampled test-process peak, with
    mem_samples and mem_boundary_samples per run.
  index_total_ms per run, against 300 s; every run listed, with range.
  Three or four runs per configuration give no useful interval; differences between A and B under 10% are
  called inconclusive. The targets are judged per run and all runs are shown.
